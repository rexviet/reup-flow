# Phase 2 — two ports, and a mutation that went red for the wrong reason

**2026-08-25** · `services/downloader` · plan `260824-2152-douyin-downloader`

Phase 2 is two adapters to the outside world: an HTTP client for the parser
fork, and a file writer. Both are small. The interesting part of the phase
was not writing them — it was discovering, twice, that a test I had already
counted as evidence was not evidence.

## What shipped

`ParserClient` over undici: four routes, envelope unwrapping, an explicit
whole-call budget, and no retries. `LocalDiskStorage`: a uniquely named temp
file per put, fsync, then `rename` as the sole commit point, plus
Content-Length verification and containment checks on keys built from data
Douyin handed us.

## The mutation that lied

The DoD asks for a specific mutation: give every write the same temp file
name, and require the two-concurrent-writers test to go red. It went red.
I recorded the guard as defended and moved on.

It was red because the losing writer's `rename` hit `ENOENT` — the winner
had already moved the shared temp file out from under it — and the test
died in the rename, several lines *before* the assertion about the
committed file's contents ever ran. The corruption assertion was never
evaluated at all.

Two things made that worse than an ordinary near-miss. First, the phase's
own write-up already promised that phase 6 will make exactly that rename
forgiving, because a worker whose lease expired has to decline to commit
rather than crash. So the mechanism the test was quietly resting on was
scheduled for deletion. Adding that tolerance and re-running gave
flaky-green: three passes in six runs, with both writers genuinely
interleaving into one file.

Second, the underlying reason the assertion was weak had nothing to do with
the rename. Both writers produced payloads of the *same length* and wrote
them at the same offsets, so whichever landed last could leave a file that
was perfectly uniform — and "uniform" was all the assertion checked. Giving
the writers different lengths, and demanding the committed file equal one
payload byte-for-byte, makes a shared file impossible to mistake for a good
one. Red four times out of four, including under the phase-6 shape.

The general lesson is narrower than "mutation testing works": a mutation
going red tells you the suite noticed *something*. Read which assertion
failed, and ask whether a change already on the roadmap removes the thing
that made it fail.

## The control that was also needed

The same mutation raised a second question I had not asked. Two mechanisms
sat on the same line — the unique temp name, and an `wx` exclusive-create
flag — and a red mutation cannot distinguish between them. So the suite now
has a mutation that must stay **green**: drop only `wx`, keep unique names,
and require the suite to survive. That is what actually shows which
mechanism carries the invariant. It is now a standing rule in the plan.

## An invariant that could not be tested where it lived

`freeBytes()` has to choose `bavail` over `bfree`, because `bfree` counts
blocks only root may use and a disk preflight built on it would accept a job
that fills the disk for everyone else. The test compared against `df` with a
tolerance. On APFS the two numbers differ by exactly zero bytes; on ext4 the
default reserve is exactly 5%, which is the tolerance. So the guard was
defended by a comment that no filesystem available to us could contradict.

Injecting `statfs` fixed it. A stub returning `{bavail: 100, bfree: 500}`
pins the choice deterministically on any machine, and the `df` comparison
stays as a sanity check against reality. Not every invariant can be proven
against the real dependency, and reaching for injection is sometimes the
honest move rather than the lazy one.

## F4 has two directions

The plan's F4 says the parser flattens every internal exception into an
HTTP 400 carrying the literal string `"An error occurred."`, so this client
must never claim to know why a 400 happened. There is a mutation for that.

The direction I had missed is the mirror image. The fork returns any Douyin
200 body verbatim and stamps its own `code: 200` on it, so a refusal at
Douyin's application layer — `{"status_code": 8, "user": null}` — arrives
looking like a completely healthy exchange. Phase 7's probe reads a
successful `fetchUserProfile` as "the cookie is still good". Discarding
`status_code`, as the first implementation did, would have made that probe
report a banned cookie as healthy and send an operator off to investigate
the profile instead.

The plan had already conceded the premise without my noticing: phase 5's
structural blocked signal is an empty `aweme_list` with `has_more=1`, at
HTTP 200. If 200 does not mean success there, it does not mean success in
the probe either. `status_code` is now surfaced on all three return types —
`null` when absent, never defaulted to `0`, because inventing a success that
was never observed is the same mistake as inventing a cause.

## An invariant that lived in another file

The no-retry rule exists because Douyin rate-limits by IP, so a hidden
retry multiplies the request rate of an enumerate loop that believes it
issues one call every three to five seconds. The client did not retry, and
the tests proved it.

They proved it about a client using undici's *global* dispatcher. Any
library in the process calling `setGlobalDispatcher(new RetryAgent(...))`
turns one parser call into four, without touching a line of
`parser.client.ts` — which means no mutation of that file could ever catch
the regression. Measured: one request became four. The client now owns a
private `Agent`, which brings the invariant back inside a file a mutation
can reach, and incidentally gives phase 4 something to close during
graceful shutdown.

## The red I nearly re-ran away

Near the end, one `pnpm test` reported two failures. The five runs after it
were clean.

The tempting reading is "transient, moving on". The correct one is that
`testSchemaName()` names each suite's private Postgres schema after the jest
*worker* — and worker ids restart at 1 on every invocation. Two overlapping
runs both claim `test_migration_w8`, and whichever reaches
`DROP SCHEMA ... CASCADE` first deletes the other's tables mid-test.

Reproducing it deliberately, with four overlapping runs, produced 22 to 35
failures each, all in db suites, all reported as `already exists` and
`relation ... does not exist`. Nothing in that reads as "you ran the suite
twice". It reads as a broken claim query — which, in a project whose entire
design rests on `FOR UPDATE SKIP LOCKED`, is the most expensive wrong
conclusion available. The comment in `test/support/db.ts` had predicted this
exact failure mode as the reason schema isolation exists; it just had not
gone far enough.

Adding `process.pid` took it to zero. A phase-0 spike file was worse still —
a bare table in `public`, where one run's `TRUNCATE` blocks behind row locks
another run's harness is deliberately holding open — and it now gets the
same isolation. Four overlapping runs, all 143 green, no schemas left
behind.

## What is not done

The `v.douyin.com` short-link DoD line is unverified: Douyin mints those per
share and they cannot be fabricated. The client half is proven — three tests
show the URL is forwarded verbatim, with no URL parsing on this side — but
the end-to-end run needs a live link. It is recorded as an expected-failure
with a banner rather than a skip, because a skipped test reads as "fine".

This environment also has no Douyin cookie at all, which turned out to be a
free demonstration of F4: two different routes, the same information-free
400, and the real cause completely invisible.

And `fsync` before `rename` has no mutation test, because there is no way to
simulate power loss in jest and a spy on `open()` would only restate the
implementation. That is written down as a declared exception rather than
papered over with a test that looks like coverage.
